# TinyWarp 0.1.1：更新菜单实时状态

日期：2026-11-12。版本 `0.1.1`，构建 `3`。本阶段修复已发布 `0.1.0` 的展开菜单状态滞后，不改变应用身份、数据目录、更新源、安装器或关于页样式。

## 行为与实现

`Workspace` 之前只订阅 `UpdateAvailable` 事件并重绘自身，独立 `Menu` 的 items 仅在打开时生成。更新状态机在检查、下载、完成、失败恢复与取消重启时已经发出模型通知，因此改为观察 `AutoupdateState`；菜单展开时重新生成 items，并通知外层重绘。

刷新复用原菜单 view，不移动焦点、不主动关闭菜单，不使用轮询。原所选项仍可用时按菜单项身份重新定位，避免插入重启项导致索引错位；原项消失或禁用时选择首个可用项。关闭的菜单不会因更新通知重新展开。

- 检查：`正在检查更新…`，禁止重复触发。
- 下载与校验：`正在下载并校验更新…`，禁止重复触发。
- 准备完成：出现 `更新已就绪，重启 TinyWarp`。
- 正在重启：`正在重启更新…`；取消后恢复就绪动作。
- 无更新或失败恢复：重新允许检查；沿用现有检查结果与错误提示。

下载和校验共享现有 `DownloadingUpdate` 阶段，没有新增耗时统计、百分比或网络阶段推断。0.1.0 的约 32 秒记录仍代表整轮检查、下载与校验。

版本配置递增后，修正打包测试写死 `0.1.0` 的夹具：TinyWarp 分支读取根配置，原 Warp 通道仍保留独立固定预期。没有新增依赖、锁文件或数据库 schema 修改。

## 聚焦验证

新增 `local_terminal_open_menu_tracks_update_notifications_without_reopening`：只打开一次真实 Workspace 菜单，经真实模型通知核对检查、下载、就绪、重复检查、无更新、失败状态、重启和取消恢复；检查焦点、选择保留、忙碌项失效、键盘导航及关闭后不重开。阶段注入仅在测试中可用，调用状态机原有通知方法，不提供产品级状态覆盖入口。

修复前该回归实际失败：模型已进入检查，菜单仍显示 `检查 TinyWarp 更新`；其余 33 项通过。修复后 34 项 Rust 回归与 5 项 Python 版本／打包测试通过，覆盖既有版本、签名、传输、下载重试、已下载包复用和本地菜单边界。测试使用临时 HOME 与系统沙箱禁止访问日常及 Preview 数据。本机未安装 nextest，沿用已有 Cargo 测试构建与隔离测试程序运行方式，单线程运行涉及全局通道配置的回归。

严格 Clippy（应用 lib、tests、`warp-oss`）通过，最后只对本轮 Rust 文件执行项目相同配置的 formatter；未在格式化后重复测试或 lint。没有运行完整 presubmit、全仓库测试或跨平台云验证。

私有日志、辅助脚本及证据位于忽略目录 `.note/0.1.1-menu/`，失败复现另存 `red-evidence/`。

## 菜单顺序调整与正式候选：构建 4

用户指出菜单项顺序与分隔线不自然后，本轮进一步收敛为两组：

```text
设置
键盘快捷键
────────
检查更新 / 检查更新中… / 下载并校验中… / 重启并更新
查看日志
```

第一组是常用配置，第二组是更新与诊断。更新始终占一行，不再与“检查更新”并排新增重启行；没有可见维护项的平台不生成孤立分隔线。重启期间显示 `重启更新中…`，取消后回到 `重启并更新`，继续沿用更新模型通知刷新。

同时修正共享菜单键盘边界：初始向下／向上跳过禁用项，全禁用时不选中任何项；Enter 激活入口拒绝不可选项。两项新增回归与现有菜单测试一起运行，没有改公开动作名称、存储格式或更新安装协议。

最终 53 项相关 Rust 回归、5 项 Python 测试、真实 GUI 的“展开菜单 → Down → Enter → 设置 → 返回终端”路径、应用与 integration runner 两组严格 Clippy 通过；最后对本轮 Rust 文件格式化。真实 GUI 已取得新的分组截图，默认深色普通文字的像素对比度为 13.606:1。完整审阅、原始依据及未验证范围见 [菜单界面审阅](0.1.1-interface-review.md)。

这份正式候选使用 `0.1.1（构建 4）`，替代前述仅在本地保留的构建 3，不覆盖既有候选或公开资产。用户已授权发布 0.1.1，后续从干净的最终实现提交构建；公开发布结果另行补记。发布后用户通过日常 TinyWarp 检查更新、升级并验收菜单，Agent 不直接替换或退出日常应用。
