# 正常退出后 Tab 丢失调查

2026-11-16，用户最初确认反馈发生在正常退出应用、再次打开之后；此前主动关闭的那批标签另行记录，不作为丢失复现。本轮完成隔离基线与故障诊断，没有改变生产恢复、关闭或写入语义，也没有操作日常数据库。

## 最新使用反馈

用户随后反馈：启用“关闭所有窗口后退出”后，Tab 似乎已经恢复，认为此前现象与这个设置有关。当前按这条最新反馈记录，不再将其描述为已经确认但仍未解决的现场丢失故障。

这是用户的使用反馈，不是 Agent 新增恢复修复或复现根因的结果；没有据此宣称所有退出方式与异常读取场景均已通过。下面保留实际运行的隔离基线和故障注入证据，两项读取风险不能倒推成此前现场现象的原因。

## 当前保存契约

- `restore_session` 默认开启，读取最近保存的窗口、标签、分屏与目录；Pinned Tab 是同一快照中的标记，不是独立备份。
- 另存 Tab 配置使用配置目录下的 TOML，与 SQLite 自动恢复分开。
- 普通退出会终止并等待 SQLite writer，处理已经排队的快照；更新重启另有 `SnapshotAndConfirm` 提交确认，失败会取消更新。
- 主动关闭窗口会改变布局快照；macOS 默认不在最后窗口关闭时退出，“关闭所有窗口后退出”的设置会影响退出路径。用户最新反馈见上节；本轮隔离基线没有对该开关的两种状态做完整对照。布局恢复不等于已退出的 shell／SSH／CLI 继续运行。

## 已运行的隔离验证

使用独立 `v0.1.2-dev.2` 应用身份、临时 HOME 与数据禁令，通过键盘创建 2 个 Tab、3 个终端 pane，执行一条测试命令；关闭设置后用 `⌘Q` 正常退出。重新打开同一测试副本，三个 shell 启动，原 UUID、工作目录、标签与测试历史一致，再正常退出，两个退出码均为 0。这次没有复现用户的间歇丢失，不能据此宣布问题修复。

另编译并运行 3 项真实 SQLite 诊断测试，其中两项调用实际 `sqlite::initialize`，没有手写一套初始化替身。测试在独立子进程、临时 HOME／Integration 通道下执行，并先断言数据库路径位于临时根；外层沙箱禁止日常与 Preview 数据访问。

| 场景 | 实际结果 | 可支持的结论 |
| --- | --- | --- |
| 正常初始化、提交快照并退出 writer | 通过，最新标题、旧终端标识与历史保留 | 初始化与普通快照排队／drain 基线可用，不代表全部 GUI Quit 时序已覆盖 |
| 必要读取失败后提交新默认窗口 | 保护旧 Tab 的目标断言失败：旧终端标识被新快照覆盖，历史行仍在 | 读取失败没有阻止旧布局被后续快照覆盖，已在真实初始化路径复现 |
| 已存在缺失 pane 引用 | 目标断言失败：读取返回成功却丢掉整个 Tab | `.ok()?` 过滤把局部读取失败伪装成成功，后续保存可能固化缺失 |

必要读取故障通过改名临时库的 `commands` 表注入。缺失 pane 在临时库关闭外键后注入坏引用，再恢复外键；正常写入受到外键保护，不会直接产生此状态。首次测试的删除被外键拒绝，未触达目标行为；修正夹具后重新编译，才得到表中的第二项故障结论。

实际结果为 1 通过、2 个保护目标失败，属于诊断证据，不是已修复测试通过。补丁与完整测试源私有归档于 `.note/product-foundation-2026-11-16/session-failure-regressions.patch` 和同目录 `session-failure-sqlite_tests.rs`；本轮追加的红测试已移出主工作区，原有测试保持不变。后续实施保护修复时再接入回归，不使用 `should_panic` 或放宽断言掩盖问题。

当前日常日志中未发现本轮筛查的持久化读取、初始化、writer 启动与快照错误文本；只记录次数，不输出私人命令。这不能排除旧日志轮转、静默 pane 过滤或其他时序问题，尚无证据把故障夹具的原因归到用户那次丢失。

## 独立风险与尚未批准的方案

故障注入暴露的读取保护风险作为独立事项保留，不作为用户现场根因，也不因用户反馈恢复可用就把失败诊断记为通过。用户尚未批准下面的生产行为变更，本轮不实施；是否继续、优先级及具体方案需另行确认。

此前提出的候选方案仅针对 TinyWarp LocalGui：必要恢复读取失败时，不启动 writer、不打开可输入的新终端，使用现有原生提示说明“无法读取上次会话，为保护原有标签，本次停止启动”，提供查看日志后退出／直接退出；不删库、不自动恢复备份。正常读取、主动关闭、Full／TUI／daemon 保持既有契约。

单个 pane 的真实读取错误也应显式处理，不能静默丢标签；已知旧 MCP 面板的预期过滤、CodeReview 及可选 JSON 的既有降级需要分别保留并测试，不能一概称为数据库损坏。

这会改变恢复失败时的用户行为，属于核心会话读写路径，实施前须确认具体方案。现阶段没有新增第二套布局存储、持久化状态或提示 UI。
